# Baseline, 9 Nov 2026 (M4 slice 1)

The first measurement through S3 (ADR-0021), before any M4 work: the reference for M4's targets (`docs/targets.md`).

## Environment

| | |
|---|---|
| What | baseline at 0f6baf3, ceesafec 0.24.1, default StoreConfig |
| Host | Apple M1, darwin 27.0.0 (macOS laptop, internal SSD, `F_FULLFSYNC`) |
| Client | `tools/bench` (go1.27.3), loopback, plain HTTP, SigV4 with UNSIGNED-PAYLOAD |
| Run | `tools/bench.sh -sizes 0,128,1024,4096,16384,65536,262144,1048576 -concurrency 1,8,32,128 -ops 1000` |
| Seed | 1; every GET body checked by MD5; fsck clean afterwards |
| Raw data | `2026-11-09-baseline.json` |

## Findings

1. **Writes are serialized: one sync per write, about 200 writes/s at any concurrency.**
   - PUT, overwrite and DELETE hold at 150 to 220 ops/s for every size up to 64 KiB, at concurrency 1, 8, 32 and
     128.
   - Syncs per 1,000 writes are 1,000 throughout.
   - More clients only queue: a 0-byte PUT's p99 goes from about 9 ms at concurrency 1 to 700 ms at 128.
   - This is ADR-0008 §4: each PUT is its own journal commit, under the store's lock. The group commit across
     requests that §4 left to M4 is the first thing to build.
2. **Reads of stored bytes cap at about 2,300 ops/s.**
   - HEAD, and GET of a 0-byte object, reach 9,000 to 16,000 ops/s.
   - GET of any inline object (128 B to 64 KiB) stays near 2,000 to 2,300 from concurrency 8 up.
   - The inline record is read from the journal, and verified, while the store's lock is held (`openUnpinned`), so
     reads queue behind one another and behind writes.
3. **Some phases stall for hundreds of milliseconds.**
   - 1 KiB GET at concurrency 1 reaches 194 ops/s with a p99 of 69 ms, against 1,728 ops/s for 128 B.
   - 4 KiB GET and HEAD at concurrency 32 reach about 300 and 1,000 ops/s, with p99 over 500 ms.
   - Hypothesis, to verify: the upkeep (ADR-0017) takes a checkpoint under the lock once 64 MiB of journal has
     accumulated, which these runs reach repeatedly.
4. **Large objects:** 1 MiB PUT reaches about 100 MiB/s and GET about 650 MiB/s at concurrency 32. Write
   amplification is 1.00 to 1.04, as expected for a log.
5. **Memory:** server RSS peaked at 288 MiB, in the 1 MiB phases at
   concurrency 128. Each request holds a 1 MiB body buffer (`BODY_STEP`). With 1,000 keys per phase and deletes
   between phases, these runs do not show memory per object; that needs a large-key-count run.
