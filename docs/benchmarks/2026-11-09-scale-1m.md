# Scale at 1M objects, 9 Nov 2026 (M4 slice 6)

The first measurement of T9 (memory), T10 (listing) and T11 (recovery), with `tools/scale.sh` (ADR-0021 amendment),
at commit `ff04ce0` (M4 slice 5).

## Environment

| | |
|---|---|
| What | `tools/scale.sh`: 1,000,000 objects of 128 B in one bucket, written by 128 clients; ceesafec 0.24.1, default StoreConfig |
| Host | Apple M1, darwin 27.0.0 (macOS laptop, internal SSD, `F_FULLFSYNC`) |
| Client | `tools/bench` (go1.27.3) in its `fill` and `list` modes, loopback, plain HTTP |
| Memory | The server's physical footprint (`footprint -p`), which counts compressed pages. A first run read `ps` RSS and was discarded: RSS fell from 54 MiB to 3 MiB while idle, as macOS compressed the index's pages. |
| Checks | Every listing page checked for the 1,000 keys that follow, in order; fsck clean afterwards (1,000,000 objects, no problems) |
| Raw data | `2026-11-09-scale-1m.json` |
| Load | Load average 7 to 10: other sessions ran a Parallels VM and builds. The latencies here are upper bounds; the memory and recovery numbers depend little on load. |

## Findings

1. **T9, memory: about 360 bytes per object.**

   | Footprint | MiB | Per object |
   |---|---:|---:|
   | Empty server | 4.9 | |
   | After the fill | 368 | |
   | After 30 s idle | 350 | 362 B |
   | After a restart (recovered from the checkpoint) | 349 | 361 B |

   - The index holds each key, its metadata and its locator; 128 B payloads stay in the journal segments.
   - The footprint fell back after the fill, and a recovered server holds the same, so the index does not grow by
     itself.
   - **But listing leaves memory behind.** 60 pages took the footprint from 350 to 379 MiB, and on the recovered
     server from 349 to 485 MiB, where it stayed. Each page builds a list of every matching key's index position (8
     MB at 1M keys) and sorts it; the allocator keeps what that touched.
2. **T10, listing: about 160 ms per page of 1,000, against 20 ms.**

   | ListObjectsV2, max-keys 1000 | p50 | p99 |
   |---|---:|---:|
   | First page | 164 ms | 175 ms |
   | Middle (start-after key 500,000) | 87 ms | 102 ms |
   | Last 1,000 keys | 9.3 ms | 11.8 ms |

   A page scans the whole index (a hash map), collects the keys after the marker, and sorts them. Its cost follows the
   keys after the marker, not the page: about 160 ns per key. This is the ordered index ROADMAP M4 lists.
3. **T11, recovery: 0.87 s from launch to serving** after a SIGKILL. The server had checkpointed after the fill (a
   168 MB checkpoint at 1,000,001 records), so recovery read the checkpoint and an empty tail. A discarded run that
   was killed with about 33,000 records past its checkpoint recovered in 0.96 s.
4. **The fill shows stalls (T7).** 1,000,000 PUTs ran at 5,128/s, p50 23 ms and p99 60 ms, but the slowest took
   446 ms (380 ms in the discarded run). The store writes its checkpoint, 168 MB here, under its lock. A checkpoint's
   cost grows with the object count, and every request waits for it.
