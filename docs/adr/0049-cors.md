# ADR-0049: CORS

**Status:** accepted for M5 (item 7, first part), 13 Nov 2026, and built (`src/store/cors.cee`, `src/s3/cors.cee`,
`src/s3/server.cee`, `src/s3/serve.cee`, `src/store/checkpoint.cee`).

## Context

- **A browser asks before it lets a page use another origin's answer.** For a request that is not simple it first
  sends a *preflight*: OPTIONS with `Origin`, `Access-Control-Request-Method` and, for the fields the script sets,
  `Access-Control-Request-Headers`. It goes on only if the answer allows them. For every cross-origin answer it
  hands the script the body only if `Access-Control-Allow-Origin` names the page's origin.
- **S3's CORS configuration** is up to 100 rules on a bucket: origins and headers as patterns with one `*`,
  methods (GET, PUT, POST, DELETE, HEAD), headers a script may read, and how long a preflight's answer may be
  kept.
- **What needs it here:** browser form uploads (ADR-0018), presigned URLs used from a page (ADR-0011), and public
  buckets read by scripts (ADR-0043, ADR-0045). Until now OPTIONS was answered by the web server itself with 204
  and an `Allow`, and no answer had a CORS field.

## Decision

1. **A bucket's CORS rules** are a `BucketConfig` record of kind 9, in a compact form: for each rule an id, the
   methods, the age, and three lists (origins, headers, exposed headers). Checkpoint format 12 adds them to a
   bucket's entry; formats 1 to 11 load. Put-, Get- and DeleteBucketCors; NoSuchCORSConfiguration for a bucket
   without rules. A rule needs an origin and a method (MalformedXML); a method that is none of the five, a pattern
   with two `*`, or more than 100 rules is InvalidRequest.
2. **A request that names an `Origin`** gets, on whatever its answer is (an error too), the fields of the first
   rule that allows the origin and the method:
   - `Access-Control-Allow-Origin`: the origin, or `*` when the rule's pattern is `*`;
   - `Access-Control-Allow-Methods`: the method;
   - `Access-Control-Expose-Headers`: the rule's, if it has any;
   - `Access-Control-Allow-Credentials: true`, unless the origin is `*`;
   - `Vary: Origin, Access-Control-Request-Headers, Access-Control-Request-Method`.
   - The method is the request's own, or the one it names in `Access-Control-Request-Method`, as RGW reads it.
     Origins are compared as they are; no rule, no fields, and the request is served as if it had no origin: CORS
     is the browser's to enforce, and never refuses a request that is not a preflight.
3. **A preflight** (OPTIONS on a bucket or a key) is answered without a signature, before authentication:
   - without `Origin`, or without a method of the five in `Access-Control-Request-Method`: InvalidRequest (400);
   - 200 with the fields of §2, `Access-Control-Allow-Headers` (the headers asked for) and
     `Access-Control-Max-Age` (the rule's, if it has one), when a rule allows the origin, the method, and every
     header asked for, compared without regard to case;
   - AccessForbidden (403) otherwise: no rules, no rule that allows it, or OPTIONS on the service.
   - A preflight never reaches a policy or an ACL: it says only what the bucket's CORS rules say.
4. **The cost.** The server keeps a count of buckets with CORS rules, made from the store at start and again
   after PutBucketCors, DeleteBucketCors and DeleteBucket, before the response. While it is 0, a request's
   `Origin` is not looked at. Otherwise a request with an `Origin` reads its bucket's rules: one turn of the
   store's lock, an index lookup. Policy actions: `s3:GetBucketCORS` and `s3:PutBucketCORS` (the delete too).

## Consequences

- A page on another origin can read, upload to and delete from a bucket whose rules allow it, with form uploads,
  presigned URLs or signed requests.
- A bucket's CORS rules can be read by anyone who sends a preflight: they are not a secret, and a preflight that
  is refused tells only that.
- OPTIONS on any path now reaches the S3 handler: without CORS rules it is 403 or 400 where it was 204.
- A store with CORS rules, or checkpointed by this build, has checkpoint format 12.
- The allowed methods of an answer are the one method asked about, not the rule's list. A browser asks about one
  method at a time, so nothing is lost, and it is what the Ceph tests expect.

## Rejected

- **Refusing a cross-origin request no rule allows:** S3 does not; the same request from a client that is not a
  browser has no origin to check, so it would protect nothing.
- **Answering a preflight for a bucket without rules with 200 and no fields:** a browser treats that as a
  refusal anyway, and 403 says why.
- **Looking at the rules for every request with an `Origin`** without the count: a lock round on requests that,
  on most stores, no rule is waiting for.
- **CORS on the service (ListBuckets):** S3 has no rules above a bucket.
