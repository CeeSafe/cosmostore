# ADR-0045: An ACL compatibility mode

**Status:** accepted for M5 (item 3, slice 3), 13 Nov 2026, and built (`src/s3/acl.cee`, `src/s3/policy.cee`,
`src/metadata/model.cee`, `src/store/object_store.cee`, `src/store/checkpoint.cee`). It closes item 3.

## Context

- **Clients still send ACLs.** `x-amz-acl: public-read` on a PUT is the oldest way to publish an object, and tools
  call GetBucketAcl and PutObjectAcl as a matter of course. Until this ADR every such call was NotImplemented.
- **S3's ACLs** grant five permissions (READ, WRITE, READ_ACP, WRITE_ACP, FULL_CONTROL) on a bucket or an object to
  canonical users, to accounts by email, and to groups: everyone, every authenticated requester, log delivery.
- **There is one account here** (ADR-0043 §1). Its keys may do what no policy denies them; the only requester an ACL
  can let in is the anonymous one. The public-access block already stores two ACL settings that do nothing
  (ADR-0044 §3).
- **The choice made with the user** (13 Nov 2026): canned ACLs and grants are stored and enforced, with the block's
  two ACL settings applied to them, rather than accepted and ignored.

## Decision

1. **An ACL is the permissions of three grantees:** the owner, everyone (`AllUsers`) and every authenticated
   requester (`AuthenticatedUsers`). The owner is the one account: canonical id and display name `cosmostore`, as
   the listings already name it. An ACL is stored as three characters, one per grantee, each `@` plus the bits of
   its permissions (READ 1, WRITE 2, READ_ACP 4, WRITE_ACP 8, FULL_CONTROL 16). The private ACL, the owner with
   full control and no one else, is stored as nothing.
   - **A bucket's ACL** is a `BucketConfig` record of kind 6. Checkpoint format 9 adds it to a bucket's entry;
     formats 1 to 8 load.
   - **A version's ACL** is a field of its metadata, `x-amz-acl`, beside its tags (ADR-0017): written with the
     version, and changed in place by a SetTags record of a second format (its first byte 2, its last field the
     ACL), which leaves the version's id, ETag, generation, time and tags as they were. A build before this one
     refuses such a record, as it refuses a newer checkpoint.
2. **Three ways to give one,** each of which becomes those three sets:
   - **a canned ACL** (`x-amz-acl`): `private`, `public-read`, `public-read-write`, `authenticated-read`;
     `bucket-owner-read` and `bucket-owner-full-control` are the private one, there being one owner;
     `aws-exec-read` and `log-delivery-write` are NotImplemented; any other name is InvalidArgument;
   - **grant fields** (`x-amz-grant-read`, `-write`, `-read-acp`, `-write-acp`, `-full-control`): `id="cosmostore"`
     and `uri="..."` for the two groups. With `x-amz-acl` too: InvalidRequest;
   - **the document** (`<AccessControlPolicy>`): an `<Owner>` and at most 100 grants. MalformedACLError for a
     document that is not one.
   - A canonical user other than the owner, the owner named as another, or another group is InvalidArgument; a
     grantee by email is UnresolvableGrantByEmailAddress: there is no one else to grant to.
3. **The calls:** GetBucketAcl, PutBucketAcl, GetObjectAcl and PutObjectAcl (with `versionId`), and the ACL fields
   on CreateBucket, PutObject, CopyObject, CreateMultipartUpload and POST object (its `acl` field). An object
   written without them is private. A copy never has its source's ACL. PutObjectAcl makes no new version.
   GetObject and HeadObject do not return the stored field.
4. **What an ACL opens:** an anonymous request that the bucket's policy neither refuses nor allows may do what the
   ACL grants everyone.

   | Permission | On a bucket | On an object |
   |---|---|---|
   | READ | `s3:ListBucket`, `s3:ListBucketVersions`, `s3:ListBucketMultipartUploads` | `s3:GetObject`, `s3:GetObjectVersion` |
   | WRITE | `s3:PutObject`, `s3:DeleteObject` | |
   | READ_ACP | `s3:GetBucketAcl` | `s3:GetObjectAcl`, `s3:GetObjectVersionAcl` |
   | WRITE_ACP | `s3:PutBucketAcl` | `s3:PutObjectAcl`, `s3:PutObjectVersionAcl` |
   | FULL_CONTROL | all of these | all of these |

   - **A Deny of the bucket's policy wins** over any ACL, as over the policy's own Allow.
   - **A key is never refused by an ACL,** whatever it grants the owner: every key is of the owner's account, and
     an ACL that leaves the owner out can always be replaced. So a grant to `AuthenticatedUsers` changes no
     decision: the authenticated requesters are the keys. It is stored, returned, and counted as public.
   - An object's ACL is its own: a public-read object in a private bucket can be read, and a private object in a
     public-read bucket cannot.
   - A request for a key or version that is not there meets the private ACL: AccessDenied, not NoSuchKey, for an
     anonymous request that may not list the bucket, as in S3.
5. **The public-access block's ACL settings** (ADR-0044 §3) now mean something:
   - `BlockPublicAcls`: a request that gives a public ACL, one with any grant to either group, is AccessDenied:
     PutBucketAcl, PutObjectAcl, and a PutObject, CopyObject, CreateMultipartUpload or POST object that carries one.
     ACLs already stored stay.
   - `IgnorePublicAcls`: the bucket's ACL and its objects' open nothing while it is on. They are still stored and
     returned.
   - **GetBucketPolicyStatus** (ADR-0044 §2) also answers `true` for a bucket whose ACL is public, unless
     `IgnorePublicAcls` is on. `RestrictPublicBuckets` stays about the policy.
6. **The cost.** A key's request is as before: nothing is read unless some policy has a Deny (ADR-0043 §8). An
   anonymous request is no longer refused at once when no bucket has a policy: it reads its bucket's policy, block
   and ACL under one turn of the store's lock, and, when those neither refuse nor allow it and the action is one an
   object's ACL can grant, the version's metadata under a second. Both are index lookups. A request that gives a
   public ACL reads the bucket's block once more.

## Consequences

- `aws s3 cp --acl public-read` and its like work, and what they publish can be fetched without credentials.
- An anonymous request costs a lock round where it cost nothing. It is the price of object ACLs: whether one object
  is public is known only at the object.
- A store with a bucket ACL, or checkpointed by this build, has checkpoint format 9; a journal with a PutObjectAcl
  has a record an older build refuses.
- The Ceph ACL tests that still fail need a second account (the `alt` user, expected to be refused or granted to)
  or compare the owner's id and display name with their configuration's.
- CreateBucket with an ACL writes two records, the bucket and then its ACL. A crash between them leaves a private
  bucket, which opens nothing.

## Rejected

- **Accepting ACLs and ignoring them:** a client that asks for `public-read` and gets a 200 expects the object to
  be public, and one that sets `private` on a public object expects it closed.
- **Grants to other canonical users or by email:** there are none to name. Accepting and dropping them would
  return a different ACL than was put.
- **Enforcing ACLs on keys:** an owner who removes their own grant would lock every key out of an object with no
  one left to restore it, and the one account's keys are its owner.
- **A count of public ACLs to keep anonymous requests free:** bucket ACLs could be counted as policies are, but
  object ACLs are per version, and the count would have to be kept through every put, delete, overwrite, expiry and
  recovery. Kept for when a measurement asks for it.
- **A configurable owner id and display name:** it would pass more of the Ceph tests, which compare both with
  their configuration; nothing else needs it yet.
