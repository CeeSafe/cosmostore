# ADR-0075: STS, temporary credentials (M7 item 4)

**Status:** accepted, 16 Nov 2026 (the owner: "Yes, accept ADR-0071 to 0077"); proposed the same day for M7 item 4 (ADR-0071), under the owner's standing go-ahead.

## Context

- AWS STS hands out temporary credentials: an access key id (`ASIA…`), a secret and a session token, which sign
  requests until they expire. `GetSessionToken` gives the caller's own rights; `AssumeRole` gives a role's, which its
  policy (and an optional session policy) bound. Clients (SDKs, the CLI, CI systems) use them so that long-term keys
  stay out of jobs and browsers.
- CosmoStore has no IAM: every key of the credentials file owns everything (ADR-0043 §4), and bucket policies can only
  deny it something or name it as a principal.

## Decision

1. **The calls.** `POST /` on the S3 port with STS's form body (`Action=GetSessionToken` or `AssumeRole`,
   `Version=2011-06-15`), signed with SigV4 for the `sts` service over the body's hash (STS's clients send no
   `x-amz-content-sha256`); answers and errors are STS's XML. Only a long-term key calls them: temporary credentials
   do not make more (AccessDenied). `GetSessionToken`: 900 s to 36 h, 12 h by default. `AssumeRole`: `RoleArn`
   (`arn:aws:iam::<any account>:role/[path/]<name>`), `RoleSessionName`, 900 s to the role's maximum (1 h by
   default), and an optional `Policy` of up to 2,048 bytes (`MalformedPolicyDocument` if it is not one CosmoStore
   takes). Without `serve --sts-key-file` they are NotImplemented. Any other parameter AWS acts on (`PolicyArns`,
   `Tags`, `TransitiveTagKeys`, `ExternalId`, `SerialNumber`/`TokenCode`, `SourceIdentity`, `ProvidedContexts`, a
   `Policy` on GetSessionToken) is NotImplemented, never taken and dropped (the M7 review's A1).
2. **Roles** are `serve --roles-file` lines, read at start: `<name> <max session seconds, 900 to 43200> <identity
   policy JSON on one line>`. An identity policy is a bucket policy's grammar without `Principal`, its resources
   `*` or any `arn:aws:s3:::…`. **Any key may assume any role**: a key already owns everything, so a role can only
   narrow what its session may do, never widen it, and there is nothing to trust or refuse.
3. **What a session may do.** A `GetSessionToken` session is its key, until it expires. A role session is its key
   narrowed: before anything else, the role's policy and the session policy must each allow the action on the
   resource (`bucket`, `bucket/key`, or the service for `ListAllMyBuckets`), and neither deny it; then the bucket's
   policy is read as for the key (a Deny naming the key applies). The check sits in `gateDecision` and ahead of
   `authorize`'s fast path for keys, which every call goes through (copy sources, DeleteObjects' keys and governance
   bypass too), and in front of the three calls that have no bucket policy: `ListBuckets` (`s3:ListAllMyBuckets`),
   `CreateBucket` (`s3:CreateBucket`), and the stats and admin API (`_cosmostore`), which no session reaches.
4. **The token is the session.** The access key id, secret, parent key, role, session name, session policy and
   expiry are sealed with AES-256-GCM (ADR-0046's cipher) under the first key of `--sts-key-file` (`<id> <base64 of
   32 bytes>` lines, like the SSE key file: the first seals, any opens, so keys rotate), with the key's id in the
   clear and in the authenticated data. Nothing is stored. A request with `x-amz-security-token` (or
   `X-Amz-Security-Token` in a presigned URL) is checked by opening it: a token that does not open is InvalidToken,
   an expired one ExpiredToken, one whose key id is not the request's or whose parent key the credentials file no
   longer has is InvalidToken, and the signature is checked with the token's secret. A role the roles file no longer
   has makes its sessions InvalidToken at the next start. The secret is wiped once the signing key is made.
5. **Logs** name the session's access key id as the requester; rate limits count it as its key's.
6. **A cluster's S3 port** had no STS keys at first: STS was NotImplemented and tokens InvalidToken. ADR-0078 §2
   gives the nodes the same key and roles files (`cosmostore node --sts-key-file`, `--roles-file`).

## Consequences

- `stsTokens` (round trip, rotation, another key, a changed byte, non-tokens), `stsRolesAndIdentityPolicies`,
  `stsFormBodies`; the S3 smoke runs `aws sts get-session-token` and `aws sts assume-role` and signs with what they
  return: the session reads and writes; a changed token, the wrong secret, STS from a session, the admin API from a
  session are refused; the role reads and lists its bucket, and is refused writes, deletes (single and batch),
  `ListBuckets`, `CreateBucket`, another bucket and a copy; a presigned URL of the role works; a session policy
  narrows the role.

## Rejected

- **Sessions in the store** (a table of tokens): a write per `AssumeRole`, and a cluster would have to replicate it;
  a sealed token needs neither, at the cost of no revoking a session before it expires but by removing its key from
  the credentials file or its role from the roles file.
- **Roles as their own principals in bucket policies** (`arn:aws:sts::…:assumed-role/…`), as AWS has them: with every
  key an owner, a role's session is its key narrowed, and bucket policies keep naming keys.
